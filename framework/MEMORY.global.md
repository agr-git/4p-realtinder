# MEMORY.global.md — Aprendizajes transversales del framework

> Aprendizajes que **le sirven a cualquier proyecto**: gotchas del entorno, rate limits de APIs compartidas, patrones de arquitectura que funcionaron, decisiones que definen el framework mismo.
>
> Este archivo viaja con la plantilla (`framework/`). Al instalar o actualizar el framework en otro proyecto, se copia junto con `FRAMEWORK.template.md`.
>
> **Limitación conocida:** en polyrepo la propagación es manual — actualizar este archivo en un repo no lo actualiza en los demás. Si el framework llega a vivir en un repo propio, este archivo se muda allí y los proyectos lo consumen desde una sola fuente.

**Formato:** ver `MEMORY.md` del proyecto. Mismas reglas: evidencia obligatoria, más recientes arriba.

## Registro

- **2026-07-27 — Ninguna integración de scraping debe quedar incompleta: enriquecer desde la página de DETALLE:** VO Propiedad y Administra B. se cargaron a PRODUCCIÓN con `beds`/`baths` en null porque su página de LISTADO no los trae (solo el detalle) — inaceptable, lo detectó el usuario en la UI (cards con "—"). **Lección sistémica:** el listado NO es fuente confiable del esquema completo; la página de **detalle** Wasi sí, y tiene esquema **consistente entre sitios**: `<li><strong>Alcobas / Ambientes:</strong> N</li>`, `Baño(s):`, `Área Construida:`, `Estrato:`. **Regla:** el pipeline corre `enrich_from_detail()` — para todo inmueble con hab/baños/área en null, baja su detalle y rellena (incl. estrato exacto). El `check_completeness()` delata 0% por campo. Así CADA sitio nuevo se completa solo, sin nulls en prod. **Evidencia:** parser de detalle probado (VO → 3 alcobas/2 baños/70m²/estrato 4; Administra usa `Baño:` singular → label tolerante `Ba[ñn]o`). Implementado en `execution/scrape_wasi.py`.

- **2026-07-26 — Los sitios "Wasi" NO comparten un solo selector set:** El supuesto de `docs/ARCHITECTURE.md` §2 (7 sitios Wasi = un parser compartido) es falso. Distintas instalaciones de Wasi renderizan las tarjetas distinto: castrorosero/vopropiedadraiz/administrabienes usan íconos (`<i class="fal fa-bed"><span>N</span>`, `fa-shower`, `class="area"`) en la HOME; luciaprada pone las features como TEXTO en `<div class="info_details">` ("3 Habitaciones / 2 Baños / 2 Garaje / 121 Área m²") y solo muestra todos los detalles en las páginas `/s/venta` y `/s/arriendo`, no en la home. **Evidencia:** las cards de luciaprada salían sin habitaciones/baños/área; el inspect del usuario apuntó a `/s/venta`, donde `fa-bed`=0 pero `info_details`=12. Se resolvió con variantes de parser por sitio (`execution/scrape_wasi.py`). **Por qué importa:** cada sitio (o grupo) necesita su variante; no asumir un parser único. Bonus: `/s/venta` es la página de resultados con paginación → vía para traer más registros (Fase de escala). Y gruporepublica/gomezchaljubb/cima dan 0 con el parser de íconos: tienen aún otra estructura, pendiente de revisar.

- **2026-07-21 — PostgREST/Supabase upsert exige `?on_conflict=<columna>` si la dedup no es por la PK:** Un `POST /rest/v1/<tabla>` con `Prefer: resolution=merge-duplicates` resuelve conflictos sobre la PRIMARY KEY por defecto. Si la deduplicación es por otra columna `UNIQUE` (aquí `dedupe_key`, con PK = `id`), sin `?on_conflict=dedupe_key` el segundo POST choca con la constraint y devuelve **409**, sin actualizar la fila. **Evidencia:** test de idempotencia sobre `listings` — sin `on_conflict`, intento 2 → `409` y `updated_at` congelado; con `?on_conflict=dedupe_key`, intento 2 → `200`, una sola fila, y `updated_at` avanzó ~2.4s (disparó el trigger). **Por qué importa:** el nodo HTTP de escritura del scraper (#3) DEBE apuntar a `/rest/v1/listings?on_conflict=dedupe_key`; si no, cada listing ya visto devolverá 409 y se rompe el refresco de `scraped_at` (y con él la lógica de staleness `is_active`).

- **2026-07-21 — `supabase db query --linked` se cuelga en entorno no-interactivo:** El comando abre conexión Postgres directa y necesita la contraseña de la base; el CLI la lee del Keychain de macOS, que dispara un prompt de contraseña de login imposible de responder sin terminal interactiva → cuelga hasta timeout. **Evidencia:** dos ejecuciones seguidas en la sesión del 2026-07-21 quedaron colgadas y hubo que matarlas (una llegó a background task `bj7q1877k`). **Por qué importa:** para verificar cosas de una base Supabase remota desde el agente, usar la **REST API con la publishable key** (no pide contraseña), o exportar `SUPABASE_DB_PASSWORD` como env var antes de `db query`. Aplicar migraciones sí funciona: `supabase db push` no toca el Keychain.

- **2026-07-21 — n8n en Docker: el volumen del host debe ser `1000:1000` o crashea en bucle:** Un directorio de volumen recién creado con `mkdir` queda de `root:root`, pero n8n corre como `node` (uid 1000) y no puede escribir `/home/node/.n8n/config` → `EACCES: permission denied` → reinicio infinito. **Evidencia:** al crear `n8n-main` en hostinger-vps, el contenedor reportó versión pero entró en `Restarting`; los logs mostraban `EACCES ... open '/home/node/.n8n/config'`; el volumen estaba en `0:0` mientras el de `n8n-staging` estaba en `1000:1000`. Se corrigió con `chown -R 1000:1000 /opt/n8n-main/data`. **Por qué importa:** al montar un contenedor n8n nuevo, `chown -R 1000:1000` el volumen ANTES de `docker compose up`. Aplica a cualquier imagen que corra como usuario no-root sobre un bind-mount.

- **2026-07-21 — Migrar credenciales entre instancias n8n exige la MISMA `N8N_ENCRYPTION_KEY`:** Las credenciales se exportan cifradas con la key de la instancia origen; si la instancia destino tiene otra key, importan pero quedan indescifrables. **Evidencia:** migración de 6 credenciales de `n8n-staging` a `n8n-main`; se leyó la `encryptionKey` del `config` de staging y se fijó explícita en el compose del nuevo contenedor, evitando re-teclear secretos. **Por qué importa:** para consolidar/mover n8n sin reconfigurar credenciales, fija `N8N_ENCRYPTION_KEY` = la del origen; nunca dependas de la auto-generada (se pierde si el volumen se borra).

- **2026-07-21 — `.gitignore`: `tmp/` no cubre `.tmp/`:** Son patrones distintos; un `.gitignore` con `tmp/` deja pasar todo el contenido de `.tmp/`, que es el directorio de intermedios del framework (Sección 7). Hay que listar ambos. **Evidencia:** el `.gitignore` inicial de `4p-realtinder` (commit dbd2c95) traía solo `tmp/`; se corrigió en 2a062a4 tras contrastarlo contra la Sección 7 del framework. **Por qué importa:** los intermedios se habrían commiteado en silencio, y en un repo público eso puede significar publicar datos scrapeados con información personal.

- **2026-08-07 — launchd no puede ejecutar scripts dentro de `~/Downloads`, `~/Documents` ni `~/Desktop` (TCC):** un `LaunchAgent` que apunte ahí falla con `Operation not permitted` **aunque el archivo tenga permisos 755 y el mismo comando funcione a mano en la terminal**. No es un problema de permisos POSIX: es la protección TCC de macOS, y el proceso que necesita el permiso es `launchd`, no el script. **Evidencia:** job `com.realtinder.keepalive` apuntando a `~/Downloads/AI/.../execution/keepalive.sh` → `/bin/bash: ...: Operation not permitted` en `StandardErrorPath`, mientras `bash execution/keepalive.sh` en la terminal corría OK. Se resolvió copiando el script a `~/.config/` (no protegido) y apuntando el plist ahí. **Por qué importa:** al programar cualquier tarea recurrente en macOS, el script ejecutable debe vivir fuera de las carpetas protegidas — la alternativa es dar Full Disk Access a launchd, que es peor. Corolario: si el repo es la fuente de verdad, hace falta un instalador que copie, y editar el archivo del repo NO cambia lo que corre.

- **2026-08-07 — Un plan Free que se pausa por inactividad mide actividad de BACKEND, no de tráfico web:** un frontend en producción recibiendo visitas no evita la pausa si nadie toca la base de datos. **Evidencia:** el proyecto Supabase de 4p-realtinder se pausó estando el sitio de Vercel online y accesible. **Por qué importa:** el keep-alive debe golpear el servicio que cuenta (una **escritura** a la BD es la señal inequívoca; un `SELECT` puede no bastar), y conviene autenticarlo como usuario normal en vez de con credencial admin — así el ping recorre el mismo camino que un usuario real y sirve de smoke test.
